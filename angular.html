Angular & Material : où va mon style ?

Dans un projet Angular, un sélecteur ne part pas tel quel au navigateur. Sass l'aplatit, Angular le réécrit, et Material ajoute son propre DOM par-dessus. Cette partie montre chaque transformation, avec le même surlignage en direct que la partie 1.

Les 4 couches entre ton SCSS et l'écran

Quand un style « ne marche pas », une de ces quatre couches l'a bloqué. Le reste de la page en fait le tour, une par une.

1 · Sass

Aplatit l'imbrication et remplace les & (partie 1). Mon sélecteur final est-il celui que je crois ?

2 · Angular

Ajoute un attribut [_ngcontent-xxx] à chaque morceau de tes sélecteurs de composant. L'élément visé porte-t-il cet attribut ?

3 · Material

Fabrique un DOM interne (.mat-mdc-*, .mdc-*) que ton template n'a pas écrit, et place certains panneaux hors de ton composant. L'élément est-il à moi, à Material, ou dans un overlay ?

4 · La cascade

Si plusieurs règles visent le même élément, la plus spécifique gagne, puis la dernière écrite. Ma règle est-elle barrée dans DevTools ?

La méthode de debug en 3 gestesClic droit sur l'élément → Inspecter → onglet Styles.
Ta règle n'apparaît pas : le sélecteur ne correspond pas (couches 1 à 3). Compare le sélecteur final avec les attributs de l'élément.
Ta règle apparaît barrée : une autre règle gagne (couche 4, leçon 10).

L'encapsulation, transformation par transformation

ViewEncapsulation.Emulated (par défaut)

Angular donne à chaque composant un identifiant. Chaque balise écrite dans son template reçoit _ngcontent-id, et la balise hôte du composant reçoit _nghost-id. Puis il colle l'attribut à chaque morceau de tes sélecteurs. C'est un sélecteur d'attribut collé (partie 1, leçons 9 et 10).

      Ce qu'il y a vraiment dans un composant Material

      Quand tu écris <mat-form-field>, Material génère des balises supplémentaires à l'intérieur. Ces balises viennent du template de Material, pas du tien : elles n'ont pas ton attribut. Par contre, ce que tu écris toi-même entre les balises (<mat-label>, <input matInput>) est du contenu projeté : il garde ton attribut.

      Ton template (dossier.component.html)         Le DOM final
<mat-form-field class="amount">               mat-form-field.amount        [_ngcontent-p]  ← à toi
  <mat-label>Montant</mat-label>               └── div.mat-mdc-text-field-wrapper            ← à Material
  <input matInput>                                   ├── label.mdc-floating-label              ← à Material
</mat-form-field>                                    │    └── mat-label  [_ngcontent-p]         ← à toi (projeté)
                                                     └── input          [_ngcontent-p]         ← à toi (projeté)
      Les classes .mat-mdc-* et .mdc-* ne sont pas une APILa documentation d'Angular Material considère ce DOM interne comme un détail d'implémentation : il peut changer à n'importe quelle version. Le cibler marche aujourd'hui, et casse sans prévenir à la prochaine montée de version. La leçon 8 montre la voie supportée.
      4

      ::ng-deep sans casser l'app

      ::ng-deep dit à Angular : « à partir d'ici, n'ajoute plus d'attribut ». La partie après lui peut donc toucher n'importe quel descendant, y compris le DOM interne de Material et tes composants enfants. L'équipe Angular déconseille fortement de l'utiliser dans du nouveau code ; il n'est conservé que pour la compatibilité, mais aucune alternative directe ne l'a remplacé.

      Le bug « ça marche seulement après être passé par tel écran »Un ::ng-deep sans :host devant devient une règle globale. Angular injecte le style du composant quand il s'affiche, et le retire quand plus aucune instance n'existe. Résultat : un autre écran change d'apparence selon la navigation. Si tu vois ce symptôme, cherche un ::ng-deep orphelin.
      Si tu dois l'utiliser, la forme sûre:host ::ng-deep .classe-precise { … }, accompagné d'un commentaire qui explique pourquoi aucun token ne suffit. La portée reste limitée à ton composant et à ses descendants.

      Styler un composant enfant depuis le parent

      Principe simple : le parent gère la boîte de l'enfant (marge, largeur, position : la balise hôte est dans son template), l'enfant gère son intérieur.

      Les 4 façons propres, de la meilleure à la moins bonne

      1 · Variable CSSrecommandé
      /* party-card.component.scss */
.name {
  font-weight: var(--party-name-weight, 400);
}

/* dossier.component.scss */
app-party-card {
  --party-name-weight: 700;
}
      2 · Classe sur l'hôte
      <!-- dossier.component.html -->
<app-party-card class="highlight"/>

/* party-card.component.scss */
:host(.highlight) .name {
  font-weight: 700;
}
      3 · Input + classe
      // party-card.component.ts
highlight = input(false);
// host: { '[class.highlight]': 'highlight()' }

/* même SCSS qu'en 2 */
      4 · Dernier recours
      /* dossier.component.scss */
:host ::ng-deep app-party-card .name {
  font-weight: 700;
}
      Pourquoi la variable CSS traverse l'encapsulationL'encapsulation filtre les sélecteurs, pas l'héritage. Une variable posée sur app-party-card descend dans tous ses enfants, comme color ou font-family. C'est exactement ce mécanisme qu'utilise le thème Material (leçons 7 et 8).

      Dialogs, menus, select, autocomplete : les overlays

      Le panneau d'un mat-select, un mat-menu, un mat-autocomplete, un dialog, un tooltip ou un snackbar n'est pas affiché dans ton composant. Le CDK le place dans <div class="cdk-overlay-container">, tout en bas du <body>. Il n'est donc ni dans ton template, ni sous ton :host : même :host ::ng-deep ne l'atteint pas.

      <body>
 ├── app-root
 │    └── app-dossier [_nghost-p]
 │         └── mat-select [_ngcontent-p]   ← le champ fermé est ici
 └── div.cdk-overlay-container                ← ajouté à la fin du body
      ├── div.cdk-overlay-pane
      │    └── div.mat-mdc-select-panel.article-panel   ← ta panelClass
      │         └── mat-option × n            ← hors de app-dossier
      └── div.cdk-overlay-pane.confirm-dialog        ← panelClass du dialog
           └── mat-dialog-container
                └── app-confirm-dialog [_nghost-d]     ← son propre SCSS marche

      La solution supportée : poser ta propre classe sur le panneau, puis écrire le style dans un fichier global.

      Template / TS
      <mat-select panelClass="article-panel">…
<mat-autocomplete class="party-panel">…
<mat-menu class="row-menu">…

this.dialog.open(ConfirmDialogComponent, {
  panelClass: 'confirm-dialog',
});
      src/styles/_overlays.scssglobal
      .article-panel {
  .mat-mdc-option {
    min-height: 32px;
  }
}
.confirm-dialog {
  max-width: 480px;
}
      Et le contenu du dialog ?Le composant que tu ouvres dans le dialog (app-confirm-dialog) a son propre template : son SCSS de composant marche normalement pour ses balises à lui.

      Le thème Material 3 : une seule fois, dans styles.scss

      mat.theme · --mat-sys-*

      Depuis la version 19, le mixin mat.theme() prend tes couleurs, ta typographie et ta densité, et génère des variables CSS système (--mat-sys-primary, --mat-sys-surface…). Tous les composants Material lisent ces variables. Tes composants peuvent les lire aussi.

      src/styles.scssglobal
      @use '@angular/material' as mat;

html {
  color-scheme: light;   /* "light dark" = suit l'OS */
  @include mat.theme((
    color: (
      primary: mat.$azure-palette,
      tertiary: mat.$blue-palette,
    ),
    typography: Roboto,
    density: 0,
  ));
}
      n'importe quel composant
      .title {
  color: var(--mat-sys-primary);
  font: var(--mat-sys-title-medium);
}
.card {
  background: var(--mat-sys-surface-container);
  border-radius: var(--mat-sys-corner-medium);
}
.hint {
  color: var(--mat-sys-on-surface-variant);
}
      html  ← mat.theme() pose ici  --mat-sys-primary, --mat-sys-surface, …
 │        (variables CSS = héritées par TOUS les descendants)
 ├── app-dossier [_nghost-p]         lit var(--mat-sys-primary)  ✔ l'héritage ignore l'encapsulation
 │    └── mat-form-field
 │         └── div.mat-mdc-text-field-wrapper   Material lit ses variables  ✔
 └── div.cdk-overlay-container        les overlays aussi  ✔
      VariableUsage typique
      --mat-sys-primary / --mat-sys-on-primarycouleur d'accent / texte posé dessus
      --mat-sys-surface / --mat-sys-on-surfacefond de page / texte courant
      --mat-sys-surface-containerfond de carte, panneau
      --mat-sys-outline-variantbordures discrètes
      --mat-sys-errormessages d'erreur
      --mat-sys-body-medium, --mat-sys-title-mediumraccourcis font complets
      --mat-sys-corner-mediumarrondis cohérents
      La règle qui simplifie toutDans tes composants : jamais de couleur en dur (#1976d2). Toujours var(--mat-sys-…) ou tes propres variables --app-…. Le jour où le thème change, tu ne touches à aucun composant.

      Changer un composant Material : les overrides

      mat.<composant>-overrides(…)

      Chaque composant Material expose des tokens : des variables CSS pour sa couleur, sa forme, sa taille… Le mixin mat.button-overrides() (et ses équivalents form-field, table, expansion, dialog…) écrit ces variables sur le sélecteur de ton choix. Toutes les balises en dessous en héritent. Tu n'as besoin de connaître aucune classe interne.

      Toute l'appstyles.scss
      @use '@angular/material' as mat;

:root {
  @include mat.button-overrides((
    filled-container-shape: 6px,
  ));
}
      Une zone seulement
      .zone-fiscal {
  @include mat.button-overrides((
    filled-container-color: gold,
    filled-label-text-color: black,
  ));
}
/* génère :
.zone-fiscal {
  --mat-button-filled-container-color: gold;
  --mat-button-filled-label-text-color: black;
} */

      Démo vivante. L'intérieur de ces boutons est vraiment isolé (Shadow DOM), comme l'intérieur de Material l'est pour ton SCSS de composant. Active chaque option et compare.

      .zone-fiscal
      .zone-succession

      Trouver le nom exact d'un tokenDans la doc d'Angular Material, chaque composant a un onglet Styling qui liste ses tokens. Dans DevTools, sélectionne l'élément : les variables --mat-… apparaissent dans l'onglet Styles et tu peux les modifier en direct pour tester.
      Où l'inclureDans un fichier global, ou dans un SCSS de composant sous :host (:host { @include mat.button-overrides(…) }). Les variables posées sur l'hôte descendent dans tout le composant, sans ::ng-deep.

      Pourquoi tes styles cassent à chaque montée de version

      Ta sensation que « les règles changent » est juste : Material a changé de fondations plusieurs fois. Chaque étape a cassé du code qui ciblait des classes internes.

      v15 · 2022

      Passage aux composants basés sur MDC. Le DOM change et les classes sont renommées (.mat-form-field-wrapper devient .mat-mdc-text-field-wrapper…). Les anciens composants restent disponibles en « legacy ».

      v17

      Les composants legacy sont supprimés. Tout le CSS qui visait l'ancien DOM ne correspond plus à rien.

      v18

      Material 3 devient stable. Les API de thème Material 2 sont préfixées m2- (mat.m2-define-light-theme…).

      v19

      Arrivée de mat.theme(), des variables --mat-sys-* et des mixins mat.<composant>-overrides().

      v20

      Les variables --mdc-* sont renommées en --mat-*, avec le nom du composant en premier. Une migration existe : ng generate @angular/material:token-rename.

      Sass

      @import est déprécié depuis Dart Sass 1.80 et disparaîtra avec Dart Sass 3. Remplace-le par @use / @forward.

      La règle d'or qui t'évite 90 % de la casseNe cible que ce qui est à toi (tes classes, tes balises, la balise hôte) ou ce qui est une API (mat.theme, --mat-sys-*, overrides, panelClass). Chaque .mat-mdc-* dans ton code est une dette pour la prochaine montée de version : liste-les avec une recherche dans le projet avant chaque upgrade.

      Qui gagne quand deux règles se battent ?

      spécificité · ordre

      Ta règle apparaît barrée dans DevTools ? Le navigateur compare le poids des sélecteurs (partie 1, leçon 3). Un piège propre à Angular : l'attribut ajouté compte comme une classe. Un même sélecteur pèse donc plus lourd écrit dans un composant que dans styles.scss.

      Écrit dansSélecteur finalPoids
      styles.scss.title0 · 1 · 0perd
      dossier.component.scss.title[_ngcontent-p]0 · 2 · 0gagne
      styles.scssapp-dossier .title0 · 1 · 1perd encore
      styles.scss.dossier .title0 · 2 · 0égalité : la règle écrite après gagne
      • 1À poids égal, la dernière règle chargée gagne. Ne compte pas sur l'ordre d'injection entre global et composants : rends tes sélecteurs explicites.
      • 2Pour battre une règle Material, n'empile pas les classes et n'ajoute pas !important : passe par un token (leçon 8). Les tokens ne se battent pas, ils changent la valeur que Material utilise.
      • 3!important déclenche une escalade : la prochaine personne devra en mettre un aussi. Réserve-le aux utilitaires (.hidden).
      • 4Astuce avancée : :where(.a .b) a un poids de zéro. Pratique pour des styles de base faciles à surcharger.

      Organiser le SCSS d'un projet qui grossit

      src/
 ├── styles.scss                 ← point d'entrée global : n'y mets que des @use
 ├── styles/
 │    ├── _theme.scss            ← @include mat.theme(…) sur html                  (génère du CSS)
 │    ├── _tokens.scss           ← tes variables métier : --app-gap, --app-danger…   (génère du CSS)
 │    ├── _material.scss         ← overrides Material globaux et par contexte        (génère du CSS)
 │    ├── _overlays.scss         ← styles des panelClass : dialogs, menus, select    (génère du CSS)
 │    └── _mixins.scss           ← @mixin, @function, $breakpoints                   (ne génère RIEN)
 └── app/
      └── dossier/
           └── dossier.component.scss   ← @use 'mixins' as mx;  puis styles locaux
      src/styles.scss
      @use 'styles/theme';
@use 'styles/tokens';
@use 'styles/material';
@use 'styles/overlays';
      angular.jsonbuild › options
      "styles": ["src/styles.scss"],
"stylePreprocessorOptions": {
  "includePaths": ["src/styles"]
}
      un composant
      @use 'mixins' as mx;

:host {
  display: block;
}
.panel {
  @include mx.stack(var(--app-gap));
}
      Le piège qui fait grossir le bundleChaque fichier .component.scss est compilé séparément. Si un partial importé par tes composants génère du CSS (une classe, un @include mat.theme…), ce CSS est recopié dans chaque composant. Les partials utilisés par les composants ne doivent contenir que des $variables, @mixin et @function.

      Les 7 règles d'équipe

      • 1Le thème Material est défini une seule fois, dans _theme.scss.
      • 2Aucune couleur en dur dans un composant : var(--mat-sys-*) ou var(--app-*).
      • 3Pour personnaliser Material : un override de token, scopé par une classe de contexte (.dense-table), plutôt que global.
      • 4Overlays : toujours panelClass ou class, styles dans _overlays.scss.
      • 5::ng-deep : toujours précédé de :host, avec un commentaire qui justifie, et suivi en revue de code.
      • 6Trois niveaux d'imbrication Sass maximum (partie 1, erreur 6).
      • 7@use partout, plus jamais @import.

      Quelle approche choisirais-tu ?

      Les attributs _ngcontent / _nghost sont raccourcis pour la lisibilité. Le DOM interne de Material est simplifié et peut différer selon ta version ; seules les API (theme, tokens, overrides, panelClass) sont stables. Le transformateur reproduit les règles d'imbrication de Sass et de réécriture d'Angular (mode Emulated) pour les cas courants.
